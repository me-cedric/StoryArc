# StoryArc for Windows

**Status: waves 2 to 4 written; waves 2 and 3 compiled on CI, nothing has run on a Windows desktop.** Three parts: a WinUI 3 app (a
library window, reader windows, preferences), an interop library over the Rust
core with the pure rules the app follows, and interop tests that run those rules
and the seam against the shared corpus. The authors of waves 0 to 2 had no .NET
SDK and no Windows machine, so **nothing here has run on Windows**; see
[Wave 2: what the code holds](#wave-2-what-the-code-holds). Every Windows claim is **Known** (read in vendor text) or **Inferred**
until a spike runs it.

[ADR-0018](../../docs/decisions/0018-desktop-clients.md) supersedes the timing in
[ADR-0004](../../docs/decisions/0004-desktop-strategy.md) and chooses WinUI 3.

## Stack

| Part | Choice |
| --- | --- |
| UI | WinUI 3 on Windows App SDK **2.5.1** (stable, 2026-09-16). 1.8 left servicing on 2026-09-24, so no start on 1.x. |
| Language | C# on **.NET 10 LTS** (end of life 2028-11-14). TFM `net10.0-windows10.0.26100.0`. Platforms x64 and ARM64. |
| Shape | One single-project packaged WinUI app. Release builds use ReadyToRun and trimming. Native AOT is not enabled. |
| Floor | Windows 11 24H2, build 26100. `TargetPlatformMinVersion` and the manifest `MinVersion` are `10.0.26100.0`. |
| Chrome | `TitleBar`, Mica through `SystemBackdrop`, `NavigationView`. Chrome only: the artwork stays the interface. |
| Core | The shared Rust core, `storyarc-core`, through the C ABI crate `storyarc-ffi` (cdylib `storyarc_ffi`). |
| Seam | A hand-designed C ABI. `csbindgen` generates the `DllImport` file. C# wrappers use `SafeHandle`. Not uniffi: its C# generator lags one minor behind. Revisit above about 40 functions. |
| Page curl | Direct3D 11 swap chain in a `SwapChainPanel`, ADR-0009 shader as HLSL, input from `CreateCoreIndependentInputSource`. **Not Win2D**: 1.4.0 targets Windows App SDK 1.8 and nothing says it runs on 2.x. |
| EPUB | `WebView2` with the pinned Readium ts-toolkit renderer. Archive resources come through a custom scheme and `WebResourceRequested`. Virtual-host mapping serves folders only, so it cannot serve archive bytes. |
| PDF | `pdfium-render` with a bundled PDFium (`chromium/7881`). `Windows.Data.Pdf` has no text, search or outline API, so it fails the `ebook-reader` spec. |
| RAR | Vendored libarchive, compiled by the `cc` crate. The MSVC build needs its own config header, kept under `apps/desktop-core` so `third_party/` stays untouched. This is the largest risk of that item. |
| SMB | An in-app Rust client (`smb`, with `smb2` as the swap-in). Not the OS redirector: it hides encryption and dialect, and Windows 11 24H2 requires signing by default. |
| Secrets | `keyring` v4 with `windows-native-keyring-store` (Credential Manager, `CredWrite`) behind a `SecretStore` trait. Keep each blob under 2,560 bytes. |
| Packaging | MSIX. The Microsoft Store is the canonical channel. Registration is free and the Store signs the package. |

Not chosen: Avalonia (draws every control itself), .NET MAUI (renders through
WinUI 3 anyway), WPF (maintenance mode), Electron and Tauri (the
`native-experience` spec forbids web-view UI outside EPUB reflow).

## Folder layout

```
apps/desktop-windows/
├── build.ps1                       the Windows build entry
├── global.json                     pins .NET SDK 10.0.401
├── Directory.Build.props           shared build properties
├── StoryArc.Windows.slnx           the solution
├── src/
│   ├── StoryArc.Windows/           WinUI 3 app (the only Windows-only project)
│   │   ├── Strings/<lang>/         Resources.resw, generated by `pnpm strings:desktop`; do not edit
│   │   └── Tokens/                 StoryArcTokens.xaml, a copy of `pnpm tokens:build`'s dist/windows output
│   └── StoryArc.Interop/           net10.0 library: hand-written wrappers over NativeMethods.g.cs, no WinUI reference
├── tests/
│   └── StoryArc.Interop.Tests/     net10.0 tests; run on Windows, Linux and macOS
└── README.md
```

The Rust side lives in `apps/desktop-core/` (`storyarc-core`, `storyarc-ffi`) at
the repository root workspace. `StoryArc.Interop.csproj` links
`apps/desktop-core/storyarc-ffi/generated/NativeMethods.g.cs`, the `DllImport` file
csbindgen writes from the Rust source, with a `<Compile Include>`; lane C owns that
file, and the interop project does not compile until it exists.

The shell reads its strings through `ResourceLoader` (the `tab_*` names for the four
destinations, the `*_empty*` sentences for the empty states) and its window title
from the package display name. The brand accent is the chrome accent: `App.xaml`
aliases `SystemAccentColor` and its six shades to the `StoryArcBrandAccent` token.

## Build and run

```powershell
pwsh apps/desktop-windows/build.ps1      # core, interop tests, then the WinUI project
```

On any OS with the .NET 10 SDK and Rust, the interop layer builds and tests
without Windows:

```bash
pnpm test:desktop:core        # cargo test -p storyarc-core -p storyarc-ffi
pnpm test:desktop:interop     # cargo build -p storyarc-ffi && dotnet test apps/desktop-windows/tests/StoryArc.Interop.Tests
```

Requirements on Windows: Windows 11 24H2, Visual Studio 2026 (or the .NET SDK and
the `winapp` CLI), the Rust toolchain with `x86_64-pc-windows-msvc`, and Developer
Mode for `winapp run`. Unsigned dev builds run through `winapp run` or an
unpackaged `dotnet publish`. A sideloaded MSIX needs a trusted certificate:
`winapp cert generate`.

CI: `.github/workflows/desktop-windows.yml` on `windows-2025-vs2026`. It is
path-filtered, so mobile CI is unaffected.

## What it inherits

Everything in the 17 capability specs holds. The parity audit finds 60 of 95 main
requirements hold as written on Windows, and 27 need a desktop reading. The
format layer, connectors, download queue and progress merge come from the Rust
core, not from a Windows implementation. `packages/design-tokens` gains a C#
emitter, `StoryArcTokens.cs` ([ADR-0007](../../docs/decisions/0007-design-token-pipeline.md)).

## Desktop-new features

Menu and keyboard reading, two-page spreads by window shape, full screen, one
window per reader, open from Explorer (file association, drag and drop, command
line), pointer reading (wheel zoom, hover chrome, right-click), live folder
watching, media keys, Jump List recent items. Later: Explorer thumbnails (a shell
extension cannot run on managed .NET, so it needs a native shim), `storyarc://`.

## Wave 2: what the code holds

Written without a .NET SDK and without Windows: the `Desktop Windows` workflow is the
first compiler, and [`desktop-conformance-windows-wave2.md`](../../docs/delivery/desktop-conformance-windows-wave2.md)
says which scenario is tested, which is wired and unwalked, and which is not started.

### The seam, in `StoryArc.Interop`

Every handle is a `SafeHandle` that frees once and holds a reference while a call runs;
calls on one handle are serialised. A failed call throws `StoryArcException` with the
core's `StoryArcStatus` and its own sentence in `CoreMessage`.

| Call | Export | What it does |
| --- | --- | --- |
| `NativeCore.Version()` | `storyarc_core_version` | The core's version string. |
| `NativeCore.RoundTrip(bytes)` | `storyarc_buffer_roundtrip`, `storyarc_buffer_free` | Bytes through the core and back. |
| `NativeCore.LastError()` | `storyarc_last_error` | This thread's last failure, or `null`. |
| `new CancelToken()`, `Cancel()`, `IsCancelled` | `storyarc_cancel_token_*`, `storyarc_cancel` | A token a folder scan watches. |
| `ComicFolder.Open(path, cancel?)` | `storyarc_folder_open` | Scans a folder; `NotFound` when it is not there, `Cancelled` when the token fires. |
| `ComicFolder.Records()` / `RecordsJson()` | `storyarc_folder_records` | The folder's publications as `CorePublication` records. |
| `ComicPublication.Open(path)` | `storyarc_publication_open` | Opens a CBZ, CBR, CBT or image folder; CB7 is `Unsupported`, by name. |
| `PageCount`, `Metadata()` / `MetadataJson()` | `storyarc_publication_page_count`, `storyarc_publication_metadata` | The page count and the record. |
| `DecodePage(index, maxPixelSize)` | `storyarc_publication_decode_page` | RGBA, not premultiplied, at most `maxPixelSize` on the long edge. |
| `ProgressStore.Open(path)` | `storyarc_store_open` | Opens or creates the progress store. |
| `Read(identity)` / `ReadJson`, `Write(progress)` / `WriteJson` | `storyarc_progress_read`, `storyarc_progress_write` | One position per publication, in the phones' JSON shape. |

The JSON shapes are `CoreIdentity`, `CorePublication` and `CoreProgress` in `CoreRecords.cs`,
read with System.Text.Json source generation.

### Pure rules, tested on any host

| Folder | Holds |
| --- | --- |
| `Library/` | `CoreLibrary` (a core record as a `LibraryRecord`, Continue reading, Up next), `HomeShelves`, `PublicationDetail`, the grid and list view model, the query state |
| `Reader/` | `PageNavigator` (pairs by window shape, the same page across a resize), `PagePixels` (RGBA to premultiplied BGRA, the decode size), zoom, keys, pointer, drag, full screen |
| `Opening/` | `OpenRequest` (what a drop, the command line or Explorer opens and refuses), `LaunchArguments` (the Windows command line), `RecentItems` (the Jump List's list) |
| `Sources/` | `FolderSourceList` (the stored folders and their availability), `RescanSchedule` (a burst of changes is one rescan, a share is polled every 10 seconds) |
| `Progress/` | `ProgressWriter` (the five-second cadence), `CoreProgressStore` (positions into the core's store) |

### The app, in `StoryArc.Windows`

| File | Does |
| --- | --- |
| `Program.cs` | `Main`: single instance through `AppInstance.FindOrRegisterForKey`, a second launch redirects its files here |
| `Shell/AppHost.cs` | The windows, the commands, the session, the progress writer, opening files |
| `Shell/LibraryService.cs` | The folder sources, their scans through the core, the watchers, the recent list and the refusals |
| `Shell/Activations.cs`, `Drops.cs`, `JumpLists.cs` | Explorer and command-line activations, drop targets, the Jump List |
| `MainWindow.xaml` | Title bar search, Home, the library `ItemsView` in grid or list, the filter and sort flyouts, the sources row |
| `PublicationDetailPage.xaml` | The detail page in the content frame |
| `ReaderWindow.xaml`, `Reader/ReaderPageView.cs` | The page view over the decoder |

## Wave 3: sources, secrets, sync and downloads

Written, like wave 2, without a .NET SDK: [`desktop-conformance-windows-wave3.md`](../../docs/delivery/desktop-conformance-windows-wave3.md)
says which scenario is tested, which is wired and unwalked, and which is not started, and lists
the gaps found in the core's seam. Test command: `pnpm test:desktop:interop`.

### The seam, in `StoryArc.Interop`

| Folder | Holds |
| --- | --- |
| `Network/` | `CoreRuntime` (one runtime; every handle made from it keeps it alive), `CoreHttp` (catalogue, Kavita, a download with its `[UnmanagedCallersOnly]` progress callback; one client per transfer), `SmbShare`, `PinBook` and `CertificateChallenge` |
| `Credentials/` | `CredentialVault` over the core's vault (Credential Manager), `SourceCredentials` (the 2560-byte rule, one outcome per save) |
| `Data/` | The queue's rules (`DownloadQueues`, `QueueOp`), the shelves (`ShelfRules`, `ShelfOp`, `ShelfEditQueue`), `LibraryDocuments` (import, export, sync, sealed credentials), `Diagnostics`, `StorageBytes` |
| `Downloads/` | `DownloadCoordinator` (metered, retry, quit, resume) over an `IDownloadTransfer`; `CoreDownloadTransfer` is the real one |
| `Sources/` | `NetworkSourceList` (no secret field; a sign-in typed into an address is split out), `SourceProbe`, `SourceFailure` (each problem named apart) |
| `Sync/` | `LibrarySyncRunner`: at start without blocking, at quit within five seconds and only when the position changed, grey when the folder is away |
| `Export/` | `DiagnosticReport` and `DiagnosticFile` (a save that names its failure), `StorageUsage` (each store sized and cleared), `DiskFull` |
| `Library/ShelfScreens.cs` | `PinnedShelves`, `ShelfPageModel`, `ShelfMembership`, `ShelfMemberId`, `HomeShelfRows` |

### The app, in `StoryArc.Windows`

| File | Does |
| --- | --- |
| `Shell/NetworkServices.cs` | The one owner of the runtime, the vault, the sources, the queue, the sync and the shelves; moves each change to the interface thread |
| `SourcesPage.xaml` | The sources, each with its state in grey; the add sheet, Test, Browse, Rename, Remove |
| `DownloadQueuePanel.xaml` | The queue in a flyout beside the Downloads title |
| `ShelvesPage.xaml` | Every shelf and one shelf's page; pin, rename, delete, reorder |
| `PreferencesPage.Wave3.cs` | Unmetered only, storage and Clear, the sync folder, the diagnostic export |
| `Shell/SourceMessages.cs` | The sentence for each source problem, from the shared catalogue |

New state in `LocalFolder`: `network-sources.json`, `certificate-pins.json`, `download-queue.json`,
`shelves.json`, `pinned-shelves.json`, `shelf-edits.json`, and the `downloads` folder. None holds a
credential. The manifest gains `internetClient` and `privateNetworkClientServer`.

## Wave 4: EPUB, PDF, the player and read aloud

Written, like the earlier waves, without a .NET SDK. The lane notes under tasks 4.16 to 4.21 of the
change say which scenario is tested, which is wired and unwalked, and which is owed to a Windows desktop.
Test command: `pnpm test:desktop:interop`; the PDF cases need `pnpm pdfium:fetch` first and skip by name without it.

### The seam and the rules, in `StoryArc.Interop`

| Folder | Holds |
| --- | --- |
| `Epub/` | `EpubPublication` (the core's manifest, positions and resources), `EpubHost` (the scheme origin, the navigation filter, every answer with its Content-Security-Policy, ranges), `RendererMessage`, `HostCommands`, `EpubProgress` |
| `Pdf/` | `PdfEngine`, `PdfDocument` (pages, text, search, outline), `PdfPaneModel` (the contents pane: outline rows, search rows, absent without a text layer) |
| `Playback/` | `PlaybackSession`, `PlaybackSpeed`, `SleepTimer` and `SleepCountdown`, `Skips`, `TransportControls` over `ISystemTransport`, `PlayerModel`, `ReadAloudModel`, `SentenceSplitter`, `XhtmlText`, `PlaybackKeepAwake` |

The egress proof runs here as `EpubHostTests.The_eight_vectors_arrive_nowhere`, over a fake of WebView2's
pipeline (`Support/FakeWebView2.cs`: the policy, the navigation handlers, the resource filter), and
`EpubSeamTests` serves the fixture book and the pinned bundle by digest. The page itself,
`apps/desktop-web/epub/test/egress.html` in the real web view, is the walk a Windows desktop owes.

### The app, in `StoryArc.Windows`

| File | Does |
| --- | --- |
| `EpubReaderWindow.xaml` | A `WebView2` on an environment that registers `storyarc-epub` (`CoreWebView2CustomSchemeRegistration`), a `*` filter into `EpubHost.Answer`, `NavigationStarting` and `FrameNavigationStarting` cancelled off the origin, no new windows; the renderer's `locator` feeds the progress cadence; Read Aloud |
| `Shell/OpenedEpub.cs` | The core handle, the host, the reading order and the sentences of a chapter for the voice |
| `ReaderWindow.xaml` | Reads a PDF through `OpenedPublication.OpenPdfAsync` with the same page view; the contents pane behind Show Contents |
| `Shell/PlaybackService.cs` | The one `MediaPlayer`, `SystemMediaTransportControls` by hand, `AudioStateMonitor` and the render-device change, `SpeechSynthesizer` one sentence ahead, the system kept awake while playing |
| `PlayerWindow.xaml` | Cover, chapter, scrub, back 15 s, play or pause, forward 30 s, speed, sleep timer, chapters |
| `MainWindow.Player.cs` | The compact bar at the foot of the library, present only while a session runs |

The project copies the pinned renderer (`apps/desktop-web/epub/dist/storyarc-epub.js`) beside the app and, when
`.build/pdfium/win-<arch>/bin/pdfium.dll` is there (`pnpm pdfium:fetch --platform win-x64`), the PDFium library too.
New state in `LocalFolder`: the `webview2` folder of the EPUB windows' user data.

Owed by a host, recorded in `docs/delivery/desktop-spike-audio-windows.md` and `desktop-a11y-windows.md`:
the egress page in the real web view, a book read end to end, a PDF walked, the eleven audio measurements,
and the Narrator walk. Seam gaps for the core owner: no identity or metadata export for an EPUB or a PDF
(the records are filed under the path), and no time-kind progress record for an audiobook.

## Open questions

1. Does the D3D11 curl hold monitor rate on a 120 Hz display while a XAML flyout animates? This is the first spike.
2. Does `dotnet build` compile the WinUI project on the runner without `setup-msbuild`? **Inferred**: yes. The MSIX step uses VS `msbuild` until a spike proves `dotnet`.
3. Can a single-project app produce an MSIX bundle? Two Microsoft pages conflict.
4. Does Store review accept `runFullTrust` for a comic reader, and does it ask for more on user-provided content?
5. Which RAR corpus results does the MSVC libarchive build give, on x64 and ARM64?
6. Is `PublishAot` workable across WinUI 3 and the interop layer? Try it only after the curl and the seam run.
7. Does 23H2 matter? The floor is 24H2. Reopen if users report 23H2 devices.
8. Signing for direct download: Azure Artifact Signing is closed to individuals outside the US and Canada. Direct download waits on a signing identity. The Store route needs none.

The full spike list, with exit criteria, is in the research file and in the
`tasks.md` of the change.
