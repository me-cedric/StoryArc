# Test plans

A plan says how somebody checks a requirement. It lives in `docs/delivery/test-plans`
as a Gherkin `.feature` file, with a `.json` sibling holding the last verdict
per scenario.

## Read this first: most of this is not your job

Konvoy does the mechanical half with buttons, and those buttons are
deterministic. Do not reproduce them by hand:

| Work | Who does it |
| --- | --- |
| Turn `#### Scenario:` into `Scenario:` | **Button** — Generate from specifications |
| Run an `@automated` scenario | **Button** — through the declared script |
| Record a manual verdict | **Button** — the tester picks it |
| Build the coverage matrix of a QA pass | **Button** |
| Draw the coverage map | **Button** |
| Invent a scenario nobody wrote | **You** |
| Decide whether a moved requirement still means the same | **You** |
| Read a failure and name the cause | **You** |

If you find yourself transcribing GIVEN/WHEN/THEN into a `.feature`, stop: press
the button instead. Your edit would drift the moment the specification moves.

## The three tags

They are ordinary Gherkin tags, so a Cucumber runner reads the same file.

- `@spec(capability/requirement)` — the requirement this scenario proves. Both
  halves are slugified: `Sign in` under `authentication` becomes
  `authentication/sign-in`. Without it the scenario is unmatched, and the
  coverage map says so.
- `@manual` — a person runs it and records what happened.
- `@automated(<script>)` — a script the project declares in its `package.json`
  runs it. The name must be one Konvoy already allows: `test`, `test:unit`,
  `typecheck`, `lint`, `test:e2e`, `e2e`, `test:bdd`, `test:features`,
  `cucumber`, `test:visual`, `test:screenshots`. Naming anything else leaves the
  scenario unrunnable.

A scenario claiming both is read as `@manual`, because asking a person is the
answer that cannot silently pass.

## Where a scenario is born

**In the specification, not in the plan.** A requirement with no
`#### Scenario:` is the gap to fill, and you fill it in
`docs/openspec/specs/<capability>/spec.md`, in the shape that file already
uses. The plan is then regenerated by a button.

Writing the scenario straight into the `.feature` looks faster and costs more:
the specification still has no scenario, so the coverage map still reports the
requirement as unplanned, and the next regeneration overwrites you.

## What you must never do to a plan

- weaken or delete an assertion so a run goes green
- raise a timeout to make a race pass
- delete a scenario because it fails
- change `@manual` to `@automated` without a script that actually covers it
- mark a verdict a person did not observe

A failing scenario is a finding. Write it in the QA pass, with the requirement
it breaches, the steps, the expectation, what happened, and a severity.

## The chain

```
specification  →  test plan  →  QA pass
```

Konvoy warns when a specification moved and its plan did not, and when a plan
moved and the pass did not. Both warnings mean the same thing: something was
copied, and the copy is now stale. Answer the warning or say why it does not
apply; do not silence it.

## Definition of done

- [ ] Every requirement in scope has at least one scenario, or a stated reason.
- [ ] Every scenario names its requirement with `@spec`.
- [ ] Every scenario says who runs it.
- [ ] No scenario references a requirement that no longer exists.
- [ ] Every failure is a finding, not a deleted assertion.
