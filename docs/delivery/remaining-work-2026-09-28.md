# What is left to build, 2026-09-28

**Date:** 2026-09-28. **Main:** `a2a42c13`. **Supersedes:** [`remaining-work-2026-08-31.md`](remaining-work-2026-08-31.md) as the work list.

This document lists the work that needs production code. It does not list tests, screenshots, device proof or documentation work. [`STATUS.md`](../openspec/STATUS.md) records test coverage. This document records what the product does not do yet, or does wrong.

## Method

1. Twenty agents each read one capability spec, or one group of open changes, against the source on both platforms. Each claim has `path:line` evidence.
2. The claims were merged. 25 claims that appeared in two or more capabilities were removed as duplicates.
3. Eight reviewer agents tried to refute every remaining claim. Each reviewer searched the whole app tree of each platform, and traced each defect from the entry point to the effect.
4. The reviewers confirmed 180 claims, narrowed 18, refuted 3, found 1 out of scope and found 4 duplicates. They also reopened 6 leads that the first agents had closed, and found 24 new gaps. A reopened or new item was read by one agent only, and its entry says so.

**The result is 225 items.** Read a `path:line` as the place to start. It is not a promise that the line has not moved.

That recount asked whether code exists for each scenario, not whether the code does what the scenario says. This pass asked the second question, and found 115 defects.

### `sources` — 4

1. **Removing a local-folder source leaves its rows on the shelf (Android)** (defect · android · S). In `unregister` (or right after it in `removeFolder`), filter `_publications` to drop rows whose `sourceId` matches the removed folder source, the same way `forget` already does for every other source kind. Evidence: `LibraryViewModel.kt:540-546`, `ScanReconciliation.kt:41-42`, `LibrarySources.swift:193-221`.
2. **A removed source's rows come back from the shelf snapshot at next launch** (defect · both · S; found by the reviewer, one agent only). On removal on both platforms, write the snapshot through as `clearSourceCache` does: clear it when the shelf is empty, otherwise write it. On Android, also call `rebuild()` in `forget`. Evidence: `LibraryViewModel.kt:686-691`, `LibrarySources.swift:216-221`, `LibrarySnapshot.kt:29-30`.
3. **30-day progress-tombstone purge is unwired on both platforms** (unbuilt-clause · both · M; narrowed by the reviewer). The purge is design intent, not a spec clause. To build it: (1) record the removed source's identities in the tombstone when the source is removed; (2) on launch, collect expired tombstones and save the registry; (3) call `ProgressStore.forget` only for identities that no remaining source holds (ADR-0006). The part of the clause that fails is the restore when a source is added again. See missed item 1. Evidence: `SourceRegistry.swift:168-178`, `SourceRegistry.kt:187-195`, `SourceRegistry.swift:168`.
4. **Adding a removed server source again does not restore its reading positions** (unbuilt-clause · both · M; found by the reviewer, one agent only). Store kind and locator in `SourceTombstone`. When a source is added, look for a tombstone with the same kind and locator. If one exists, add the source through `readding` with the old id. Evidence: `CatalogueConnection.swift:202`, `KavitaConnection.swift:171`, `CatalogueConnection.kt:225`.

## Possible additions

None of these is in a spec. Each needs `/opsx:propose` before anyone builds it (AGENTS.md §3). The first group comes from a comparison with other readers. The second group comes from the ADRs, the security review and the desktop plans.

### From other readers

| **Smart shelves from a saved filter** | library-browsing / collections-and-reading-lists | S | medium |
| **Reading statistics and goals** | reading-progress / home-screen | M | medium |
| **WebDAV source** | network-share / sources | M | medium |

- **Look up and translate a selected word.** Readers of foreign-language books, and manga readers who are learning Japanese, need a meaning without leaving the page. Apple Books offers Look Up and Translate on every selection. StoryArc removes them. iOS gives both through system APIs: UIReferenceLibraryViewController, and the Translation framework, which translates on the device. Android sends the selection with ACTION_PROCESS_TEXT to installed dictionary or translate apps. No data goes to a StoryArc service, so the privacy rules stay true.
- **Download ahead in a series.** A commuter who reads a series from Kavita, OPDS or SMB must download each next issue by hand before the connection goes away. With this addition, the app keeps the next N unread issues of the series on the device while the reader reads it. It obeys the Wi-Fi-only and storage-limit rules. With 'remove downloads after finishing', which is already specified, this makes a rolling offline window. Offline is a project non-negotiable, so the value is high and the cost is small.
- **Progress sync through a KOReader sync server.** Folders, SMB shares and OPDS catalogues cannot store progress, so a reader with a phone and a tablet has two separate positions. A KOReader sync server (kosync) is small, is self-hosted, and is already used by KOReader e-ink readers and Readest. It fits 'talks to servers the user already runs'. StoryArc would push and pull progress with the existing conflict rules. Pages in CBZ and PDF map directly. EPUB needs a conversion between an xpointer and a Readium locator, and that conversion is the main cost.
- **Komga server as a first-class source.** Komga and Kavita are the two main self-hosted comic servers. Today StoryArc reaches Komga only through OPDS. That means no two-way progress sync, no series and read-list structure, and no server search. The Kavita client already has these functions, so a Komga client can follow the same pattern: the Komga REST API, an API key, read-progress sync, read lists, collections and series. Dedicated Komga clients exist because OPDS is not sufficient.
- **App lock and private reading.** Readers who share a device, or whose library has adult content, want the app to open only after Face ID, Touch ID or the device credential. They also want to read without history, so that Keep reading and Up next do not show the book. Both platforms supply biometric APIs (LocalAuthentication, BiometricPrompt). Private reading is a switch on the progress writer. The cost is small.
- **Split or rotate a wide spread in portrait.** On a phone in portrait, a double-page spread is shown alone and at a small size, so the text in it is hard to read. Mihon offers two opt-in settings: split the spread into two turns in reading-direction order, or rotate it to fill the screen. This addition needs a spec amendment, because comic-reader now says that a wide spread is never split across two turns. The default stays unchanged.
- **Audio bookmarks and smart rewind.** A listener marks a passage in an audiobook to hear it again or to quote it. After a long pause, a listener has lost the last sentence. Smart rewind goes back a few seconds on resume, and the time it goes back grows with the length of the pause. Both additions are small and fit the player that the open change defines. The best time to add them is before that change is archived.
- **Smart shelves from a saved filter.** A reader wants a shelf that updates by itself, for example 'unread manga on this device' or 'ongoing series from Kavita'. Today a reader can combine filters, and the filters persist, but the reader cannot save a filter as a named shelf or pin it on home. This follows the owner direction to take patterns from Apple Music, where smart playlists do this. It also matches Kavita smart filters. The filter engine and pinned shelves exist already, so the cost is small.
- **Reading statistics and goals.** Many readers want to know the time they read, the number of books they finished this year, and their streak. Apple Books makes this a primary feature. StoryArc already records sessions every 15 seconds, so the data is available. The statistics stay on the device, so the privacy rules stay true.
- **WebDAV source.** Many NAS devices, Nextcloud and rclone expose files over WebDAV. Some users have no SMB. Android has no system WebDAV provider. iOS reaches WebDAV only when the vendor app installs a File Provider. The app already does ranged HTTP reads, so WebDAV needs only PROPFIND listing and authentication.
- **Audiobookshelf server as a source.** Audiobookshelf is the main self-hosted audiobook server. When the audiobooks change is complete, readers who run Audiobookshelf will still have no way to get their library into StoryArc except through file shares, and they will get no progress sync. An Audiobookshelf client gives browse, download and two-way position sync. It depends on audiobooks-and-playback.
- **Panel-by-panel view.** On a phone, a full comic page is too small to read without constant zoom. A guided view detects the panels and moves through them in reading order. Panels charges a premium for this feature, which shows that its value is high. The cost is large because the app must detect panels on the device (with Vision or ML Kit, or a model) on both platforms.
- **New-issue notifications for followed series.** A serial reader wants to know when a new issue arrives on their own Kavita or OPDS server, without opening the app. Today a refresh runs only in the foreground, and the spec forbids notifications for refresh. An opt-in background check (BGAppRefreshTask, WorkManager) that looks only at started series, with one summary notification, gives this. It touches only the user's own servers.
- **Siri, Shortcuts and Assistant actions.** A listener in the kitchen or in a car says 'resume my audiobook' or 'continue reading'. BookPlayer and Apple Books support Siri and App Shortcuts. StoryArc publishes only a user activity for the open book, plus quick actions. App Intents on iOS and App Actions or shortcuts on Android make the two resume verbs available by voice and in automations. The value increases when audio playback ships.
- **Import a reader's own font.** Some readers need a font that StoryArc does not bundle: a CJK face, a dyslexia font, or a favourite serif. KOReader and Readest let the reader add a TTF or OTF file. The registration code exists already (CTFontManager on iOS, a font asset on Android). The only new work is a file picker and the licence note.

- **Reader-chosen light/dark theme pair does not exist — the pair is a hardcoded constant.** The ebook-reader spec scenario promises the reader can choose which light theme pairs with which dark theme, so a mid-book appearance flip lands on the pair they picked. No picker and no stored pair exist on either platform: the pairing is a fixed map resolved once at reader construction. A reader who prefers e.g. Sepia-by-day/OLED-Dark-by-night cannot set that; they get whatever the code hardcodes. Source: docs/openspec/STATUS.md:49-54 (updated 2026-09-12, most current status doc): "the scenario promises 'the light and dark reading themes the reader chose as their pair', and the pair is a constant — AppearanceMode.presetMatching on Android, ThemePreset.matching on iOS. No stored pair and no picker exists on either side." Matches docs/delivery/remaining-work-2026-08-31.md row 15. Verified current: no picker/persistence code found for a theme pair.
- **SMB transport encryption is hardcoded off on both platforms — the network-share spec's encrypted-transport scenario is unmet everywhere.** network-share requires the app to state whether an SMB connection is encrypted, implying encryption is at least sometimes true. Today it is never true on either platform: SMBClient on iOS negotiates only SMB 2.0.2/2.1 (no SMB 3, so encryption is unreachable), and jcifs-ng on Android asks for it but the app's own constant reports false regardless of what negotiates. This is distinct from the already-decided (ADR-0016, risk-accepted) iOS signature-verification gap — encryption itself is simply not implemented as a capability on either side. Source: apps/android/core/model/src/main/kotlin/app/storyarc/core/model/ShareTransport.kt:27 `const val IS_ENCRYPTED: Boolean = false`; apps/ios/Packages/StoryArcKit/Sources/StoryArcCore/ShareTransport.swift:23 `public static let isEncrypted = false`; docs/decisions/0010-smb-clients.md consequences: "Neither client implements SMB 3 transport encryption... 'Encrypted' is never true."
- **Home-screen widgets: still zero code, prerequisites (shared snapshot, iOS App Group/signing team, Android Glance-vs-material3-alpha check) not started.** native-experience names widgets as a required system affordance. ADR-0011 deliberately deferred both platforms behind three prerequisites: a shared reading-position snapshot file, an iOS App Group plus a real signing team, and an Android Glance version resolved against the pinned material3 alpha. None of the three has been started. Source: docs/decisions/0011-home-screen-widgets.md (accepted as a deferral, prerequisites section). Verified today: no file named *widget* exists anywhere under apps/ios or apps/android outside build artifacts (find returned nothing).
- **Desktop apps (macOS/Windows/Linux): zero code, and the platform-neutral specs carry no desktop-specific reinterpretation yet.** ADR-0004 defers all desktop work until both mobile apps ship 1.0 — deliberate, not a gap by itself. But the desktop READMEs each list open questions (page-curl feel on desktop, reader-in-its-own-window vs. mode, App Store vs. direct distribution on macOS; Win2D/WinAppSDK version-skew risk and OS-redirector encryption visibility on Windows; GTK4-vs-Avalonia on Linux) and a table of "spec reinterpretations this target owes" (pointer vs. finger-tracked curl, Credential Manager vs. Keychain, etc.) that no docs/openspec/specs file has absorbed. When desktop work starts, that translation is a real, currently-uncaptured task, not a side effect of writing code. Source: apps/desktop-macos/README.md "Open questions" section; apps/desktop-windows/README.md "Spec reinterpretations this target owes" table and "The spike, sharpened" section; apps/desktop-linux/README.md; docs/decisions/0004-desktop-strategy.md "Open questions" (1-3) and "Revisit when".
- **CB7 (7-Zip comic archives) decision is settled in direction but deferred — no vendoring, no reader, no spec update yet.** ADR-0013 chose to eventually read CB7 (vendor liblzma/xz-utils behind libarchive) over refusing it forever, but deferred the work because vendoring xz-utils is a real supply-chain cost (xz shipped CVE-2024-3094). The refusal behaviour stands for now and is correctly implemented, but the spec's CB7 row and open question remain open pending this work — worth tracking explicitly rather than assuming "decided" means "scheduled". Source: docs/decisions/0013-cb7-support.md "Decision Outcome": "Option A, deferred. CB7 will be read one day; it is not being built now"; names the xz-utils/CVE-2024-3094 supply-chain cost as what stopped it. docs/openspec/specs/publication-formats/spec.md open question section (referenced by the ADR) still lists CB7 as unresolved.
- **The Minizip C reader linked into the iOS binary (zlib contrib code dated February 2010) has never had a security assessment, despite parsing every untrusted EPUB opened.** ADR-0014 resolved the marmelroy/Zip CVE by proving the vulnerable Swift module is unreachable, but in doing so established that the C `Minizip` module from the same package IS reachable — it is the first-choice ZIP container reader for every EPUB the app opens on iOS. Its provenance (zlib's 2010-era contrib code) was explicitly out of scope for that ADR and has never been separately audited, even though it sits on the app's primary attack surface (a hostile publication file). Source: docs/decisions/0014-unpatchable-zip-in-the-readium-graph.md, Consequences: "Neutral, and outside this finding: the Minizip sources in this package are the zlib contrib reader dated February 2010, and they parse untrusted archives on the live EPUB path. Nothing here assessed them... if an archive-parsing hardening pass is ever scheduled, they belong in it." Reachability confirmed in the same ADR: DefaultArchiveOpener tries MinizipArchiveOpener() first, and EpubReaderOpening.swift:33 uses those defaults.
