# Implementation status

What is built against what is specified, capability by capability. Written because the
change task lists track four changes and the specs describe seventeen capabilities, so
"how much of StoryArc exists" had no answer anywhere.

Keep this current. A status document that lags is worse than none, because it is believed.

## The count

The seventeen specs hold **315 scenarios** today, counted from `docs/openspec/specs/*/spec.md`.
Two of those specs -- `reading-themes` and `page-transitions` -- were split out of
`ebook-reader` and `comic-reader` on 2026-08-30 when the reader-theming change was finally
synced, which is why the audited count below is 266 rather than 315: their 31 scenarios were
read in their old homes, and the two new rows say so rather than claiming a fresh audit.
Every one of them has been read against the app source on both platforms, scenario by
scenario, with `path:line` evidence, over two audit rounds ending 2026-08-30. That produced
**269 verdicts**: three scenarios in `collections-and-reading-lists` carry two independent
clauses each, and averaging a half-built scenario is how a half-built scenario reads as
done, so those were scored twice. Where a verdict from the earlier round disagreed with the
code — reading aloud, Kavita server search, the five `sources` gaps, the two `comic-reader`
defects all landed after it was taken — the code won and the verdict was re-checked by hand
before it was written down here.

| Verdict | Count | Means |
| --- | --- | --- |
| built and tested | 137 | code on both platforms, and a test on each side asserts it |
| built, asserted by nothing | 89 | code on both platforms, no test anywhere touches it |
| one platform only | 21 | code on one side; on the other it is absent, or declared and never reached |
| missing | 21 | no running implementation on either platform |
| unclear | 1 | could not be settled from source (`localization`, long-translation layout) |

**None of those numbers says anyone watched the behaviour happen.** That is a third axis,
and it is per-row: a great deal of what landed in the last few rounds compiles, lints,
passes its unit tests and has been seen by nobody, because the Simulator control this repo
uses has been down for most of them and an emulator was not always available. Every row
below says which of its parts were driven, on what, and which were not. Where a row says
"not driven", read it literally.

A capability is **built** when every scenario has code on both platforms, **partial** when
some do, **absent** when none do. All fifteen are `partial`. Two rows were wrongly marked
`built` before this audit and are not any more; nothing here is marked `built` on optimism.

| `publication-formats` | partial | 16 scenarios: 15 built and tested on both, 1 built and asserted by nothing. **A publication's publisher, description, series and series index are read out of an EPUB, on both platforms.** The series is stated two ways and both are read: EPUB 3 defines `belongs-to-collection` refined by `group-position`, EPUB 2 defines nothing at all, and Calibre's `calibre:series` filled that gap so widely that a reader's library is mostly that. The named placeholder and the skipped count were seen on both. The spine cover was seen on the emulator's library grid, beside three text-only EPUBs still drawing their placeholder -- on the simulator the grid could not be reached, because adding a folder source needs the document picker and no input could be delivered to it. The zoom re-decode was proved on the emulator by an A/B against a throwaway build with the gain threshold raised out of reach: same page, same viewport, same fit, and the ruling is visibly finer and higher-contrast with the re-decode than without. It has **not** been driven by a real pinch on either platform -- neither `adb` nor the simulator offers a second finger -- so what is verified is the decode and what it draws, not the gesture that asks for it. | `reading-progress` | partial | 17 scenarios: 4 built and tested on both, 9 built and asserted by nothing, 1 one-platform, 3 missing on both. This is a good local store and a good merge table sitting on top of two wires nobody connected. **The reflowable progress badge stuck, and that is fixed.** On a two-chapter EPUB it climbed through chapter one and then read "50% read" on every page of chapter two, including the last page of the book. Placing a resource in the reading order was an exact string match on the locator's href, and a locator that came from a link carries the fragment the link pointed at while one from a search can carry a query -- neither is part of the resource's identity and neither matched, so the resource could not be placed at all. The lookup now lives in `TotalProgression` beside the arithmetic it feeds, ignores the fragment and the query on both sides of the comparison, and is pinned by six assertions a side including the last page of the last resource reading 100%. It cost more than a badge: the position is stored from the same number, so a wrong progression was a wrong resume point and a wrong "finished" flag. **Not confirmed on a device** -- the arithmetic and the matching are tested, but which of the two the emulator was hitting was never established. **Synchronisation pulls as well as pushes, on both platforms.** ADR-0006's table was written on both platforms, tested on both, and called by nothing -- `KavitaSync` only ever pushed, so a chapter read on a phone was invisible to a tablet until the tablet read it too. `ProgressPull` is the caller: it sorts each merge into records to write, records the server is behind on, and the conflicts that earn a sentence. Finding *which* publication a server's chapter is was the part that had to be right -- a server reports against its own chapter id and the local store keys on a publication identity, so this adds the inverse of the link Kavita already remembered and a lookup by stable id. A chapter this device never opened is skipped rather than adopted. The conflict notice is once, naming how many, and offers to take the other. Eight assertions a side on the merge itself. **Nothing has been run against a server, live or mocked** -- what is proven is the table and the sorting, not the round trip. **The finished lifecycle is built on both**: a completion timestamp stamped once and never restamped -- reopening a finished publication writes a new position, not a new completion -- a finished publication that reopens at the beginning while keeping the record, and "Start from the beginning", confirmed, offered only where there is a position to clear. ## What blocks what

`sources` is the keystone. Five capabilities wait on it, and so do the three open tasks
in `format-scope-and-libraries`:

```
sources (registry, credentials, cache, health)
  ├── opds-catalog        built on both except catalogue search, which is iOS-only
  ├── kavita-server ──── reading-progress: synchronisation pulls, and drops what it
  │                       would push; the silent-adopt rule is unreachable
  ├── network-share
  └── offline-downloads ─ comic-reader: "offer to delete the download"   built on both,
                          as a gated sweep with a ten-second undo rather than an end-screen offer
                        └ settings-and-about: clearable downloads
                        └ format-scope-and-libraries 5.2, 5.3, 6.5
```

`collections-and-reading-lists` depends on `sources` only for its server-backed half. Its
local half — a collection a reader makes themselves — is built on both platforms, with two
holes in it that belong to no server: a collection is deleted without confirmation, and its
cover cannot be chosen.

## Where the two platforms differ

They are near line-for-line equal wherever code exists. Twenty-one scenarios are not equal,
and every one of them is named in its own row above. These are the divergences that are
deliberate — the rest are gaps, not decisions.

1. **Volume-button page turns are Android-only.** Deliberate: iOS cannot capture the
   volume buttons within App Store rules, and the app says so rather than shipping a dead
   switch. `AppSettings.turnPagesWithVolumeButtons` nonetheless exists on iOS and drives
   nothing.
2. **A PDF's document outline is iOS-only.** `PDFKit` reads one and
   `android.graphics.pdf` exposes none, so the find sheet has a third tab on one platform
   and not the other -- absent, never empty. Selection, copy, marking and in-publication
   search are on both, over each platform's own PDF library.
   [ADR-0012](../decisions/0012-pdf-text-on-android.md).
3. **Android has a manual library refresh; iOS has none.** Both watch, by completely
   different means: iOS opens a kernel event source on each directory, because a vnode
   event says nothing about what happened a level down, and caps how many it opens;
   Android registers one content observer per picked folder, which already carries
   descendants. Neither has been watched working, and on iOS the foreground reconcile
   that would back them up is applied to no view.
4. **Reordering sources is a drag on iOS and two buttons on Android.** `List.onMove`
   gives iOS the drag the spec describes, and gives VoiceOver its own reorder actions with
   it. Compose has no drag-to-reorder; hand-rolling one is a long-press gesture, an
   auto-scroll and a set of semantics actions that a screen reader would still need spelled
   out — so Android mirrors the download queue in the same app, which chose two buttons for
   the same reason. Both persist the same order. A reading list reorders the same way on
   each platform, for the same reason.
5. **Predictive back is drawn by the system on iOS and, inside the app, by nobody on
   Android.** iOS pushes onto a `NavigationStack`, which animates the interactive pop
   itself. Android's in-app navigation is the app's own state, so the app would have to
   draw the preview of a screen leaving — and `PredictiveBackHost`, which does that, has no
   call sites. The system-level app-exit preview is on, so this shows up as a screen that
   leaves without previewing rather than as a broken gesture.
6. **The reader's selection menu diverges on purpose.** iOS refuses the system edit menu
   and anchors a popover of five swatches to the words; Android puts named colours into
   the `ActionMode` the platform already raises, which is where an Android reader looks
   and is also what a screen reader can read out. Both offer the four things the spec names.
7. **The cleartext exception is wider on Android.** A self-hosted catalogue usually answers
   over plain HTTP on a `.local` name or a private address. iOS says exactly that with
   `NSAllowsLocalNetworking`; Android's network security config can name a host or an IP
   literal but not a range, so the exception there covers every host. Both platforms
   complete a typed address with no scheme to `https`, so reaching a server over cleartext
   takes a reader typing `http://`.
8. **Device-driven verification is Android's.** `pnpm smoke:android` walks every route on
   a connected device and asks logcat whether the process died; `pnpm a11y:android` reads
   the real accessibility tree at real density; `pnpm pseudo:android` walks nine routes
   under `en-XA`. iOS has one simulator-bound UI test, scoped to the library and currently
   `XCTExpectFailure`d. This one is not deliberate — it is where the tooling happened to
   get built.
